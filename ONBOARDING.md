# baml-bsv-eval — Project Onboarding

## What this project is

A structured evaluation of **BAML (BoundaryML)** vs the **raw Anthropic Python SDK** for LLM structured extraction, built as a Track 1 Developer Tools evaluation for BSV Partners. The task: extract typed portfolio company update records from VC founder emails.

**Project path:** `baml-bsv-eval/`
**Python venv:** `baml-bsv-eval/.venv/` — always use `.venv/Scripts/python` (not system python)

## Schema: PortcoUpdate (10 fields)

Defined in two places (the whole point of the eval):

| Field | Type | Notes |
|---|---|---|
| company_name | string | Required |
| reporting_period | string | Required |
| arr_usd | float? | Null if hedged or not mentioned |
| customer_count | int? | Null if range or ambiguous |
| mrr_growth_pct | float? | Only if explicitly stated for MRR |
| runway_months | float? | Null if hedged |
| key_updates | string[] | High-level milestones |
| risks_flagged | string[] | Explicitly raised concerns |
| key_hires | string[] | Named joiners only, "Name (Role)" format |
| sentiment | Positive/Neutral/Concerning | Overall tone |

**Raw SDK** — schema lives in 4 places: Pydantic model, `_TOOL` description string, `_SYSTEM` prompt, module docstring. No compile-time link between them.

**BAML** — schema lives in `baml_src/extraction.baml` only. `{{ ctx.output_format }}` auto-renders it into the prompt. `/// docstrings` on fields become prompt content.

## Key findings (from bench_results.json)

### Token cost (most surprising result)
- Raw SDK tool schema (JSON Schema format): **969 tokens** per call
- BAML `ctx.output_format` (compact text format): **123 tokens** per call
- **87% reduction** for identical schema — verified via `count_tokens` API
- On 10K daily extractions: ~8.5M fewer input tokens/day with BAML

### Latency
- Raw SDK (Haiku): 2,845–3,303 ms mean
- BAML (Sonnet): 3,823–4,570 ms mean
- **Gap is model-driven, not framework-driven** — Haiku vs Sonnet
- BAML framework overhead isolated at 70–244 ms (1.5–6.4%) via direct Sonnet baseline

### Failure modes (degenerate input `email_bad.txt`)
- **Raw SDK**: silent pass — returns `company_name: "<UNKNOWN>"`. Pydantic accepts it. Downstream systems get garbage-but-valid data.
- **BAML**: `BamlValidationError: Failed to parse field company_name: Expected string, got null` — loud, field-level, catchable. 10/10 runs fail.

### Schema iteration (adding `key_hires: list[str]`)
- Raw SDK: touched 4 surfaces (~2 min), no compile-time safety
- BAML: 1 line in `.baml` + `baml-cli generate` (0.8s)

## Known Windows-specific gotchas

1. **`load_dotenv(override=True)` is required** — Windows may have `ANTHROPIC_API_KEY=''` in the OS environment. Without `override=True`, dotenv silently skips it and BAML fails at import time.

2. **BAML stderr not capturable** — BAML's Rust runtime writes INFO logs (including real token counts and latency) via the Windows Console API (`WriteConsole`), not fd 2. `os.dup2` redirection doesn't work. Use the `count_tokens` API instead for token measurement.

3. **`on_tick` callback is silent** — `b.with_options(on_tick=fn).ExtractPortcoUpdate(...)` — the callback never fires in sync mode. No error, no warning.

4. **BAML enum values must be PascalCase** — `Sentiment.Positive`, not `Sentiment.positive`. The error message is a runtime parse failure, not a compile-time warning.

5. **`count_tokens` requires at least one message** — `messages=[]` returns HTTP 400. Use a placeholder message and subtract its cost to isolate system token counts (see `count_tokens_raw()` in `bench.py`).

## Demo server notes

`server.py` serves:
- `GET /` → `demo.html` (added `FileResponse` route)
- `GET /emails` → dict of test email contents
- `POST /extract/raw` → SSE stream (prompt → result → meta → [DONE])
- `POST /extract/baml` → SSE stream (same shape)

BAML token counts in the demo are **character-based estimates** (len//4), not exact. The benchmark uses the `count_tokens` API for exact counts.

## Benchmark methodology

- **N_RUNS = 10** per email per version
- **N_OVERHEAD = 3** direct Sonnet baseline runs per email  
- **SLEEP_S = 0.4** between calls (rate limit buffer)
- **p95** = max of 10 runs (stated explicitly in output)
- **BAML tokens_in**: `count_tokens` on rendered prompt (stable across runs)
- **BAML tokens_out**: `count_tokens` on result JSON (exact per run)
- **Raw SDK tokens**: from `response.usage` (exact)
- **System token isolation**: placeholder message subtraction (see `count_tokens_raw()`)
